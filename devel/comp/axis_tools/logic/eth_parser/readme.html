AXI-Stream Ethernet Parser

ENTITY AXIS_ETH_PARSER_GEN IS

The AXIS_ETH_PARSER_GEN component reads protocol headers from Ethernet frames. The frames pass unchanged from the RX to the TX interface.

The parser is a chain of stages. PROTOCOLS sets the protocol of each stage. A stage reads the header only when the previous headers announce its protocol. Otherwise the stage passes the announced protocol and its offset to the next stage. The order in PROTOCOLS must therefore follow the order of headers in a frame. The first stage must be PROTO_ETH.

For each frame, the parser outputs one item on the HDR_* interface. Item i contains the header that stage i read. The package axis_eth_parser_types provides functions that decode HDR_DATA. The parser reads only the first get_extract_bytes(PROTOCOLS(i)) bytes of a header. A header is reported as not found when the frame ends before all bytes that the stage reads.

A register stage between two parser stages shortens the critical path and adds one clock cycle of latency. STAGE_REG_AUTO and STAGE_REG select these register stages.

ENTITY AXIS_ETH_PARSER IS

The AXIS_ETH_PARSER component parses Ethernet frames and extracts the Ethernet, VLAN, IPv4, TCP and UDP headers. It contains AXIS_ETH_PARSER_GEN with one stage for each of these protocols, so it reads at most one VLAN tag. The headers are decoded into the extracted_headers_t record on the HEADERS output interface. The original frame data passes through unchanged to the TX interface.

Limitations

  • The parser outputs only the bytes that the table lists. IPv4 options, TCP options and the data of IPv6 extension headers after byte 7 are not available.

  • A header is reported as not found when the frame ends before all bytes that the stage reads. The output does not show whether such a header is missing or cut. Bytes of the header after these bytes can be missing from the frame.

  • HDR_VLD is set only after the frame passes TX_AXI_TREADY. The TX side must not hold TX_AXI_TREADY low until HDR_VLD is set.

  • When a frame contains more headers of one protocol than PROTOCOLS has stages, the protocol chain ends after the last stage of this protocol.

  • In an IPv4 or IPv6 fragment with a fragment offset other than 0, the frame contains no TCP or UDP header. The TCP and UDP stages then read data bytes of the fragment. Check fragment_offset of IPv4, or the IPv6 Fragment header (next header 44).

  • The MPLS label stack does not announce the protocol after the last label. The PROTO_MPLS stage reads the IP version field of the next header for this purpose.

  • A next header that would start after PKT_MTU ends the protocol chain.

Register stages

A register stage after a parser stage delays the AXI data and the protocol chain by one clock cycle. It shortens the critical path from the header of one stage to the header extraction of the next stage.

  • With STAGE_REG_AUTO = true, get_stage_reg_auto(PROTOCOLS) selects the register stages. It places them after each PROTO_IPV4 and PROTO_IPV6EXT stage, except after the last stage. These stages compute a variable header length, which makes the path longer.

  • With STAGE_REG_AUTO = false, bit i of STAGE_REG adds a register stage after stage i.

Each register stage adds one clock cycle of latency and registers for one AXI word.

Example

The example parses VLAN tagged IPv6 frames and decodes the IPv6 header.

constant PROTOCOLS : proto_array_t := (PROTO_ETH, PROTO_VLAN, PROTO_IPV6, PROTO_TCP, PROTO_UDP);
constant IPV6_I    : natural       := get_stage_index(PROTOCOLS, PROTO_IPV6);
...
ipv6_hdr   <= decode_ipv6(hdr_data(IPV6_I));
ipv6_found <= hdr_found(IPV6_I);
